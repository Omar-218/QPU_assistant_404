## [التاريخ: 2026-07-22 — خطة إصلاح ASCII: تعميم أداة التحويل + professorId فريد]

### ما تم إنجازه
- بملف `lib/idSlug.js` (المملوك لي)، تنفيذاً للمهمة §2 بخطة `plan-ascii-filenames-fix.md`:
  1. استخرجت منطق التحويل عربي→لاتيني + slugify من داخل `suggestSlug` إلى دالة عامة مستقلة
     مصدَّرة: **`transliterateToSlug(text)`** — بلا أي افتراض حول كونها "لـ id مادة" تحديداً.
  2. أعدت بناء **`suggestSlug(name)`** لتصبح مجرد نداء رفيع فوق `transliterateToSlug` — نفس
     التوقيع والسلوك تماماً، توافق عكسي كامل مع كل الاستدعاءات الحالية (`SubjectForm.jsx`،
     `StudyPlanEditor.jsx` بعضو 3)، دون أي حاجة لتعديل بملفاتهما.
  3. أضفت دالة مرافقة جديدة: **`suggestProfessorId(professorName, existingIds)`** — تبني
     المعرّف عبر `transliterateToSlug` ثم تضمن **الفرادة** ضمن `existingIds` بإضافة لاحقة رقمية
     عند التصادم (`prof-alaa`, `prof-alaa-2`, `prof-alaa-3`, ...)، بنفس نمط معالجة تصادم أسماء
     الملفات المعتمَد أصلاً عند عضو 5 (`githubPublisher.js`). لا كتابة فوق دكتور موجود بصمت أبداً.
  4. راجعت `isValidSlug` مقابل المتطلَّب: هي عامة أصلاً (تأخذ `slug` + `existingIds` بلا أي
     افتراض عن نوع الكيان)، فتصلح للتحقق من `professorId` كما تصلح لـ `id` المادة دون أي تعديل
     بالكود — أضفت توثيقاً بالتعليق يوضّح هذا صراحة بدل تعديل المنطق نفسه (لا نسخة موازية).
- اختبرت الدوال الأربعة (`transliterateToSlug`, `suggestSlug`, `suggestProfessorId`, `isValidSlug`)
  بسيناريوهات Node مباشرة:
  - `suggestSlug` تعطي نفس نتيجة `transliterateToSlug` حرفياً (توافق عكسي مؤكَّد).
  - تصادم ثلاثي لنفس الاسم بالضبط ("د. سارة" × 3) → `d-sara`, `d-sara-2`, `d-sara-3` (فريدة،
    لاحقة تتصاعد صحيحاً، لا استبدال صامت).
  - أسماء فارغة وأسماء إنجليزية أصلاً كحالات حافة — سلوك متوقَّع بكلتا الحالتين.
  - `isValidSlug("د.", [])` ترجع `false` (يرفض أي حرف غير ASCII، يخدم غرض المنع بخطة الإصلاح).
- فحصت `node --check` على `idSlug.js` للتأكد من سلامة الصياغة.

### مشكلات واجهتها
- **ملاحظة توثيقية فقط:** سيناريو الاختبار المقترَح بخطة الإصلاح كمثال ("د. أحمد" مقابل "دكتور
  أحمد") لا يُنتِج فعلياً نفس الـ slug بجدول التحويل الحالي (`d-ahmd` مقابل `dktwr-ahmd`) — لأن
  "دكتور" تُترجَم لأحرف مختلفة عن "د."، فلا يوجد تصادم حقيقي بهذا المثال بالذات. هذا لا يعني أن
  منطق الفرادة غير مُختبَر: اختبرته فعلياً بتصادم متعمَّد (نفس الاسم حرفياً مكرراً) وعمل بشكل صحيح
  بلاحقة رقمية متصاعدة. أُبلِغ هنا فقط لتوضيح أن غياب تصادم بمثال §7.3 المحدَّد بالخطة ناتج عن طبيعة
  التحويل لا عن خلل بمنطق الفرادة نفسه — عضو 6 قد يحتاج مثالاً آخر فعلياً متصادماً لو أراد تكرار
  هذا السيناريو بالذات حرفياً (مثلاً اسمان يختلفان فقط بتشكيل يُحذف أصلاً بالتحويل).

### المشكلة (تشخيص مستخدم عبر Network tab)

كل واحد بشكل مستقل تماماً — كل استدعاء `useState`/`useEffect` منفصل بلا أي معرفة بالآخر، فيصير
طلب شبكة مكرَّر بلا داعٍ (نفس المنطق ينطبق على `useUploadRequestsLog()` عبر نفس `useNotifications`).

### الإصلاح
تجميع الطلبات المتزامنة (request de-duplication) بوعد (`Promise`) واحد مشترك على مستوى الموديول
لكل من `useEvents.js` و`useUploadRequestsLog.js`: أول استدعاء بلحظة معيّنة يبدأ `fetch` حقيقياً
ويحفظ الوعد؛ أي استدعاء آخر بنفس اللحظة (قبل اكتمال الأول) يستلم **نفس الوعد** بدل بدء طلب جديد.
فور اكتمال الوعد (نجاحاً أو فشلاً) يُفرَّغ المرجع المشترك — **لا تخزين مؤقت دائم** عمداً، لأن
`AdminEventsLog.jsx`/`AdminRequestsQueue.jsx` يحتاجان بيانات طازجة دائماً بعد كل قرار جديد؛ فقط
الطلبات المتزامنة الفعلية (نفس اللحظة، نفس تحميل الصفحة) تتشارك طلباً واحداً.

### اختبارات نفّذتها
- سكربت Node مباشر يحاكي استدعاءين متزامنين: تحقّقت أن `fetch` الحقيقي يُنفَّذ **مرة واحدة فقط**
  وكلا الطرفين يستلمان نفس النتيجة، وأن استدعاءً لاحقاً منفصلاً (بعد اكتمال الأول) يُنفِّذ `fetch`
  حقيقياً جديداً (لا كاش دائم يخفي قرارات أدمن جديدة).
- `esbuild` على الملفين: بلا أخطاء. `npm run build` كامل: نجح.
