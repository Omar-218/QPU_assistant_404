> وثيقة عقود هذي الدفعة. تُحسم هنا كل التفاصيل الغامضة قبل التنفيذ المتوازي —
> بعد اعتمادها، كل عضو يبني بملفاته المحدَّدة فقط بلا حاجة لمراجعة كود عضو آخر.

## 0. القرار المعماري الحاسم — محدَّث ومُعتمَد

الموقع بلا خادم إطلاقاً (GitHub Pages ثابت + جيتهاب كقاعدة بيانات، توكن كامل فقط عند
الأدمن). الطالب زائر مجهول بلا أي قناة كتابة. **قرار المستخدم الصريح: الطالب يرفع
PDF فعلياً مباشرة (لا رابط خارجي)، وموافق على تخصيص توكن مستقل لهذا الغرض.**

### التصميم المعتمَد — توكن واحد مقيَّد لكل طلبات الطالب (حدث + رفع ملف)، حماية فرع، لا دمج تلقائي أبداً
**توكن ثانٍ مستقل بالكامل** عن توكن الأدمن الكامل، صلاحياته: `Contents: Write` +
`Pull requests: Write` فقط، على هذا الريبو حصراً — **بلا صلاحية دمج أو إدارة**.
يُضمَّن بكود الموقع العام (قابل للاستخراج من أي أحد نظرياً — هذا محسوب، راجع "لماذا
آمن" أدناه). يُستخدَم لكل من طلب الحدث وطلب رفع الملف، بنفس الآلية بالضبط —
توحيداً للتدفق وتبسيطاً (بدل استخدام Issues لشيء وPR لشيء آخر).

**تدفق أي طلب طالب (حدث أو رفع ملف)**:
1. الطالب يملأ النموذج (مادة، نوع الحدث أو قسم الملف نظري/عملي/إلخ، عنوان، تاريخ أو
   ملف PDF حسب النوع).
2. التوكن المقيَّد يفتح **فرعاً جديداً** (`event-request/{slug}-{timestamp}` أو
   `upload-request/{slug}-{timestamp}`)، يكتب عليه بيانات الطلب (وملف PDF فعلي لو
   طلب رفع)، ويفتح **Pull Request يستهدف `main` — بلا دمج تلقائي إطلاقاً** (ما فيه
   أي كود بهذا المشروع يدمج بهذا التوكن، ولا حتى تلقائياً).
3. المحتوى **غير مرئي بالموقع الحي** لأنه بفرع منفصل عن `main` — عزل تلقائي بحكم
   آلية جيتهاب نفسها، بلا حاجة لمجلد "معلَّق" خاص.
4. الأدمن (بتوكنه الكامل الموجود أصلاً) يرى طابور المراجعة = قائمة PRs مفتوحة بعنوان
   يبدأ بـ`[event]` أو `[upload]`، يعاين المحتوى (الملف الفعلي بحالة الرفع)، يعدّل
   الحقول بلوحة التحكم.
5. **قبول**: توكن الأدمن الكامل يضيف/يحدّث `events.json` أو `lectures.json` (حسب
   النوع) على **نفس فرع الـ PR**، ثم يدمجه (بنفس آلية الدمج الموجودة فعلياً بـ
   `publishToGitHub`) — دمج واحد يحمل المحتوى وتسجيله معاً.
6. **رفض**: إقفال الـ PR بلا دمج — الفرع يبقى موجوداً (غير مؤذٍ، حذفه لاحقاً يدوي
   اختياري بحت، لا ضرورة برمجية).

### لماذا هذا آمن رغم إن التوكن قابل للاستخراج من الكود العام
صلاحية `Contents: Write` وحدها لا تكفي لحماية حقيقية (لو تسرّب، تقنياً يقدر يكتب أي
ملف بأي فرع). **الحماية الفعلية مصدرها قاعدة حماية فرع `main`** (خطوة يدوية بإعدادات
الريبو — راجع 0.1) تشترط مراجعة/موافقة قبل أي دمج — فحتى لو تسرّب التوكن المقيَّد
بالكامل، أسوأ سيناريو هو PRs مزعجة لا تدخل الموقع الحي أبداً بدون فعل الأدمن الصريح
(زر "قبول" الموجود فقط بتوكنه الكامل).

### 0.1 خطوات إعداد حساب مطلوبة منك مباشرة (لا يقدر عليها أي كود)
1. أنشئ Fine-grained PAT جديد بصلاحية `Contents: Read & Write` + `Pull requests:
   Read & Write` **فقط**، محدود بريبو المشروع وحده.
2. Settings → Branches بالريبو → أضف قاعدة حماية على `main` تشترط
   **"Require a pull request before merging"** — هذي الخطوة هي الحماية الفعلية،
   لا التوكن نفسه.
3. أعطيني التوكن (أو ضعه بمتغيّر بيئة `VITE_UPLOAD_TOKEN` بإعدادات النشر) بعد ما
   يجهز الكود — لا حاجة له لبدء التنفيذ، فقط قبل أول اختبار حي فعلي.

### افتراضان إضافيان ما زالا قائمَين (لم يُعترَض عليهما، سأكمل عليهما)
- صفحة الإشعارات عامة لكل الزوار (لا حسابات طلاب أصلاً).
- "إلغاء الحدث عند وصول تاريخه" = إخفاء لحظي مُشتقّ (لا تخزين "منتهي"، لا مهمة خادم)،
  مع بقاء السجل الكامل بلوحة الأدمن دائماً.

## 1. عقد البيانات الجديد

### 1.1 `public/data/events.json` — سجل الأحداث المقرَّرة (مقبول/مرفوض فقط)
الطلبات المعلَّقة تعيش فقط كفروع/PRs مفتوحة (راجع القسم 0) — لا تدخل هذا الملف إلا
بعد قرار الأدمن. هذا يجعل الملف = السجل المطلوب بلا أي كتابة إضافية.

```json
{
  "events": [
    {
      "id": "evt_1722000000_ab12",
      "subjectId": "circuits",
      "subjectName": "الدارات الكهربائية - 1",
      "type": "exam",
      "typeLabel": "امتحان",
      "title": "امتحان منتصف الفصل — القسم النظري",
      "date": "2026-08-01",
      "submittedByLabel": "طالب من الشعبة أ (اختياري)",
      "status": "approved",
      "adminNote": "",
      "prUrl": "https://github.com/OWNER/REPO/pull/42",
      "createdAt": "2026-07-25T10:00:00.000Z",
      "decidedAt": "2026-07-25T12:30:00.000Z"
    }
  ]
}
```
- `type`: `"exam" | "quiz" | "midterm" | "homework" | "other"` — لو `other` يُملأ
  `typeLabel` بنص حر كتبه الطالب/عدّله الأدمن، وإلا `typeLabel` مشتقة تلقائياً.
- `date`: تاريخ ISO يوم فقط (`YYYY-MM-DD`)، بلا وقت.
- `status`: `"approved" | "rejected"` فقط (لا `"pending"` هنا إطلاقاً).
- **"نشِط الآن؟" قيمة مُشتقّة دائماً، لا تُخزَّن أبداً**: `status === "approved" &&
  date >= today`. تُحسَب بكل مكان يُعرَض فيه (صفحة المادة، الإشعارات) — لا حاجة لأي
  كتابة "expired" لاحقة، ولا مهمة مجدولة.

### 1.2 تسجيل الملف المقبول — إعادة استخدام `lectures-*.json` الموجود حرفياً
لا عقد جديد هنا. عند قبول طلب رفع، يُضاف عنصر عادي بمصفوفة القسم المناسب
(`sections.theory/lab/extra/exam`) بنفس بنية جلسة 5 (`type`, `file`/`content`/`url`,
`title`, `hidden`) — إعادة استخدام كاملة لعقد أنواع المحتوى الموجود، بلا أي تمديد.
حقل إضافي واحد فقط اختياري للتتبّع: `"requestOrigin": "student-upload"` (لأغراض
لوحة السجل فقط، لا يؤثر على العرض للطالب إطلاقاً).

### 1.3 `public/data/upload-requests-log.json` — سجل قرارات رفع الملفات
```json
{
  "requests": [
    {
      "id": "upl_1722000000_cd34",
      "subjectId": "circuits",
      "subjectName": "الدارات الكهربائية - 1",
      "section": "lab",
      "requestedTitle": "حل تمارين الأسبوع 5",
      "fileName": "week5-solutions.pdf",
      "submittedByLabel": "",
      "status": "approved",
      "adminNote": "أعيد تسمية الملف قبل النشر",
      "prUrl": "https://github.com/OWNER/REPO/pull/43",
      "createdAt": "...",
      "decidedAt": "..."
    }
  ]
}
```
- `section`: تتبع `SECTION_LABELS` الموجودة فعلاً — إعادة استخدام حرفية، لا تسميات
  جديدة.
- هذا الملف سجل/تدقيق فقط، لا يُقرأ من صفحات الطالب إطلاقاً — فقط بلوحة سجل الأدمن.

### 1.4 صيغة عنوان/جسم الـ Pull Request (الطابور المعلَّق)
- العنوان: `[event] {subjectName} — {type} — {date}` أو
  `[upload] {subjectName} — {section} — {requestedTitle}`.
- الجسم: كتلة JSON واحدة بنفس حقول 1.1/1.3 بلا `status/decidedAt/prUrl` (تُضاف
  لاحقاً وقت القرار داخل ملفات السجل، لا داخل الـ PR نفسه).

### 1.5 الإشعارات — **مُشتقّة، بلا ملف تخزين خاص بها**
تُبنى وقت العرض من `events.json` + `upload-requests-log.json` مرتَّبة حسب
`decidedAt` تنازلياً، آخر 20 عنصراً. لا حاجة لملف `notifications.json` منفصل ولا
لأي كتابة إضافية.

## 4. قواعد أمان صريحة (بصرف النظر عمّا يُنفَّذ)

- التوكن المقيَّد **يعيش بملف واحد معزول** (`studentSubmission.js`) ولا يُستورَد
  إطلاقاً من أي ملف يستخدم توكن الأدمن الكامل — يمنع أي احتمال تسريب صلاحيات إضافية
  بالغلط.
- **لا كود بهذا المشروع يدمج PR بالتوكن المقيَّد إطلاقاً** — الدمج حصراً بتوكن
  الأدمن، وحصراً بعد فعل "قبول" صريح بلوحة التحكم.
- حماية فرع `main` (0.1) هي خط الدفاع الحقيقي — بدونها التوكن المقيَّد غير آمن كفاية
  رغم صلاحياته المحدودة اسمياً. **لا نعتبر الميزة جاهزة للنشر الحي قبل تفعيلها.**
- أي نشر ملف فعلي، حتى المقبول من طالب، يمر بنفس بنية `sections`/أنواع المحتوى
  الموجودة بكل قواعدها الأمنية (منع SVG، تحقق `url` مزدوج، إلخ) — بلا مسار مختصر.
